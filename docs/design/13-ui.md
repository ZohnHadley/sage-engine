# 13 — UI (short)

> **From the slice retrospective (2026-09-23), finding 1 — now F38.** The first vertical slice closed
> with **nothing the player can look at**: the spellmaker composes spells from the console, the
> inventory and the spellbook are console commands, and the HUD is four hand-placed rectangles. Every
> screen the slice needed turned out to be a `Log.Info`, which is why decision **D8** (Gum vs Myra vs
> our own) is still open. The next feature worth *playing* rather than *testing* is a screen. See
> [`../history/vertical-slice-2026-09-23.md`](../history/vertical-slice-2026-09-23.md).

## 1. Purpose and scope
Two different things:
1. **Developer UI:** the console, overlays, dev tools and the editor.
2. **Game UI:** HUD, menus, inventory, dialogue.

They use different technology on purpose. Expanded before inventory/dialogue screens are built.

## 3. Key decisions
- **Developer UI = Dear ImGui**, via the already vendored `third_party/MonoGame.ImGuiNet` (today's `Game1.GuiRenderer`).
  - It's used for the console (02 §4.2), `stat` overlays, dev windows and the whole editor (15).
  - Drawn in the Overlay pass (06).
  - Compiled only into dev builds and the editor host. **Not in `Shipping`.**
  - The **console** is the exception: v1 uses an ImGui window (dev builds). The `Shipping` console (`con_enable`, 01 §3.2) is a simple drop-down drawn with the game UI's font renderer, built with the game UI (D8). Built with #353: "As built (the Shipping console)".
- **Game UI = our own, on `UiDraw` (ARCHITECTURE D8, decided 2026-09-23; see "As built (the panel model)" below).** The candidates were **Gum** and **Myra** (both MonoGame UI libraries), against a small custom retained UI, on these criteria:
  - gamepad and keyboard navigation;
  - data-driven layouts (moddable, hot-reloadable);
  - text rendering with Unicode, localization keys (05) and runtime TTF fonts;
  - resolution scaling;
  - allocation behaviour;
  - licence.
- **Fonts:** anything but an MGCB `SpriteFont`, since MGCB is no longer part of the pipeline (05). A generated bitmap atlas is the v1 answer (see below); runtime TTF (e.g. FontStashSharp **[candidate, unverified]**) is the answer for localisation, when a language needs glyphs an atlas cannot hold. Built with #338 on StbTrueTypeSharp instead: "As built (fonts per style, wrap and clip)".
- **v1 HUD before the decision:** a minimal immediate-mode HUD with `SpriteBatch` in the Overlay pass: health, crosshair, interaction prompt, and a pickup message.
- **Input** for UI goes through the `UI` context (08 §3.3), and text through `Window.TextInput` (08 §3.5).
- **UI reads simulation state; it never writes it.** Buttons that do something in the game ("use item") send commands through the input/command path (04 §3.1 rule), never direct component writes.

### As built (the v1 HUD, 2026-09-23)
- **Code:** `src/Sage.Client/Rendering/UiDraw.cs` (the queue), `UiRenderSystem.cs` (Overlay phase, one `SpriteBatch`, plus the crosshair), `src/Sage.Simulation/ECS/MessageLog.cs` (player-facing messages), and the game's own HUD in `games/Sandbox.Client/Hud.cs` (it moved there with the sim/client split, R15).
- **The engine draws none of the game's HUD.** It provides three things — `UiDraw` (rectangles, frames, text and images in screen pixels), a `MessageLog` every world has, and the crosshair — and the game composes them. What a health bar looks like is a game decision, and putting it in `Sage.Client` would have made the client know what health *is*. The crosshair is the exception: combat and the Use action both aim from the centre of the screen, so not drawing one is a handicap rather than a style (`ui_crosshair`, on by default, drawn only while a camera rig has the view).
- **Immediate mode, queued in a Frame phase, drawn in Overlay.** Anything running at display rate calls `Rect`/`Text`/`Image`; `UiRenderSystem` draws the queue and clears it. There are no widgets, no layout and no UI input handling — picking a real UI library (Gum, Myra, or something custom) is still open, and this is the smallest thing that let the slice show health, hands, a prompt and what just happened.
- **`MessageLog` is in the engine, not the client**, so a system can say "you picked something up" without knowing whether anything draws it — a headless server pushes into a log nobody reads. Since R13 (2026-09-23) `world.Say(...)` sends a `Said` game event and the log is the presentation system that reads it with a cursor (04 §3.1), which is why a message goes on screen at the next frame rather than the instant a tick says it. Messages carry a `MessageKind` (Info/Good/Bad) rather than a colour, because the simulation shouldn't name colours, and a `Fade` the HUD can use so a line leaves rather than vanishing.
- **The font is a grid of pixels we drew (R12, 2026-09-24).** The HUD font was an MGCB `SpriteFont` built from Consolas, which meant the build machine needed that font installed, glyph coverage was fixed at build time, and it was the last thing keeping MGCB in the build. It is now a **5×7 bitmap atlas the repository generates**: `engine_content/tools/make_font.py` draws 100 glyphs (printable ASCII plus `↑ ↓ • × …`, the characters the engine's own hint lines use) into a 128×56 `font.png`, and `src/Sage.Client/Rendering/BitmapFont.cs` reads it. Four constants are the whole contract between tool and runtime — an 8×8 cell, a 5×7 glyph in it, sixteen to a row, first code 32 — so a character's cell is `code - 32` and there is no metrics file to fall out of step. It draws at `PixelSize = 2`: a 14 px glyph on an 18 px line, about what Consolas 15 gave, so panels keep their shape. Characters are wider than that font's — 12 px against roughly 8 — which a panel that sizes itself from `Measure` absorbs and a hard-coded width would not.

  What this buys, beyond retiring MGCB: the engine ships no font it did not draw and licences nothing; the atlas is a PNG, so it hot-reloads like any texture and a mod can replace it; and **an unknown character draws as a gap instead of throwing**, where `SpriteBatch.DrawString` threw — an em dash in a hint line or a name a player typed used to take the frame and the process with it. What it costs is real too: one size, one weight, ASCII plus five extras, and no kerning. Runtime TTF is still the answer for localisation (05 §3.7). A missing font costs the text, not the HUD: bars and the crosshair still draw, and it logs once.
- **First-person hands (2026-09-23).** An `attack` record names a `viewmodel` sprite sheet — frame 0 at rest, the rest a swing — and the HUD draws it bottom-right, picking a frame from the `Melee` component's own phase and timer. So what you see in your hands is the simulation's swing, not an animation running alongside it, and equipping a different weapon changes it because the attack record changed. Daggerfall's own first-person weapons (`WEAPON*.CIF`, one idle pose and five-frame swings) import straight into that shape; the placeholder set draws a fist with three frames. It is drawn only while a camera rig has the view, so `cam_free` doesn't leave arms floating in mid-air.
- **Allocation.** The queue is pooled and the Sandbox's HUD caches its strings, rebuilding one only when what it says changes, so frames with the HUD up still allocate nothing (02 §4.6).
- **Not built (at the time):** menus, an inventory screen, dialogue, gamepad/keyboard navigation, layout, localisation, resolution scaling beyond raw pixels, and the Shipping console (§3). Screens, navigation and the first two of those arrived with F38 the same day — see "As built (screens)".

### As built (the panel model — F38's engine half, 2026-09-23)
A screen is two things: **what to show**, which is a simulation question, and **how to draw it**, which
needed the UI library decision **D8**, which had not been made when this was written. Those separate
cleanly, so the first half was built first; D8 was then decided as our own drawing on `UiDraw` (below).

- **Code:** `src/Sage.Simulation/UI/Panel.cs` (`PanelRow`, `Panel`) and
  `src/Sage.Kits.Rpg/GameplayPanels.cs` (the builders for spellbook, inventory, the spellmaker's
  effects and the spells a world has composed; the RPG kit's since #27, see "As built (screens by id)").
  Tests in `tests/Sage.Tests/UI/PanelTests.cs`.
- **A `Panel` is a titled list of rows**, and a row is everything a screen needs about one line: the
  `RecordId` to act on, a display name, a detail string ("12 mana", "2 kg"), a count, whether it is
  **selected** (readied, equipped) and whether it is **enabled** — with, when it is not, the reason in
  words.
- **The reason comes from the rule that would refuse it**, not from a second copy of the rule. The
  spellbook asks `AbilityRules.CanCast`, the same gates `AbilitySystem` applies and the AI consults
  (16 §3.3, R17); the bag asks `Items.CanEquip`, which `Equip` itself now uses. A greyed row and a
  refused action therefore cannot disagree, which is exactly the bug this shape exists to prevent.
- **Retained and rebuilt on demand**, never per frame: a screen rebuilds when it opens and after the
  player does something, because a row holds strings and rebuilding at display rate would allocate
  per row per frame (02 §4.6). `Panel.Version` bumps on each rebuild so a screen can cache layout.
- **The engine has no screens, so the console is the screen.** `spells` and `inv` print the *panel* —
  `Panel.Log` — which is the dogfooding: the console and a future screen read the same rows from the
  same builders and cannot drift apart. `ready <ability>` is the action a spellbook screen will call
  (`world.Ready`).
- **Why this is the useful half:** a headless test can now assert what a screen would show. "The
  spellbook greys out the spell you cannot afford and says why" is a test rather than a screenshot to
  squint at, and 12 of them came with this.
- **Built on 2026-09-23** — see "As built (screens)".

### As built (screens, F38, 2026-09-23)
**Decision D8: our own, on `UiDraw`.** With the panel model already answering what a screen shows, a
library would have contributed a list, a selection and a box; Gum brings an external layout editor and
Myra its own fonts and stylesheets, and both bring a second UI model beside the one the HUD uses. They
remain the right answer the day a screen outgrows a list.

- **Code:** `src/Sage.Simulation/UI/Screen.cs` (`Screen`, `ScreenStack`) and
  `src/Sage.Client/UI/ScreenSystem.cs` (`ScreenSystem`, `PanelView`). The game says which screens it
  has: `games/Sandbox.Client/Screens.cs` is 50 lines for a spellbook and a bag. Tests in
  `tests/Sage.Tests/UI/ScreenTests.cs`.
- **The split is the point.** A screen *is* a panel, a highlighted row, and what a button does to the
  world — all simulation, so `Screen` and `ScreenStack` are in the **engine** and a headless test opens
  a spellbook, moves down, presses Enter and asserts the readied spell changed. Only the drawing and
  the reading of input are in the client.
- **A game screen is a subclass with two methods:** `Build` (fill the panel) and `Activate` (what Enter
  does), plus `Alternate` for the second button. Everything else — wrapping selection, scrolling,
  rebuilding after an action, keeping the highlight inside a list that shrank — is in `ScreenStack`.
- **Input:** a new `ui` input map in the **UI context**. It reads its own keys first and then swallows
  the rest, so nobody walks about or swings behind an open inventory; the key that opened a screen
  closes it, and Escape closes without quitting the game. `MenuUp`/`MenuDown`/`MenuConfirm`/
  `MenuAlternate`/`MenuBack`, with `Inventory` (I) and `Spellbook` (B) opening the two.
- **Drawn in Overlay, before `UiRenderSystem`**, because a game's HUD queues in FrameUpdate and the last
  thing queued is on top. The crosshair and the game's viewmodel and interaction prompt hide while a
  screen is open — they belong to aiming, and there is nothing to aim at.
- **Two bugs a screenshot found and no test would have:** an interaction prompt and a fist painted
  across the spellbook (the layering above), and both stacks of a two-sword inventory drawing the
  "equipped" tick, because the tick was per item *id* and two swords are two stacks of one.
- **One crash it also found, in the engine:** `SpriteBatch.DrawString` throws on a character the font
  was not built with, so the first hint line with an arrow in it killed the process. Fonts now load
  with `DefaultCharacter = '?'` — a missing glyph is a visible '?', never a crash — and the HUD font
  gained the few glyphs the screens use.
- **Not built:** tabs or columns, drag and drop, and any screen that is not a list or a list with a
  field. (On the widgets since: tabs with #340, drag and drop with #346.)

### As built (the mouse, F38, 2026-09-23)
The piece that decided whether the layout should be a *type*. It should.

- **Code:** `src/Sage.Simulation/UI/PanelLayout.cs` — where a screen's box, rows, field, reason and hint
  are, as plain arithmetic over a viewport size and a line height. `PanelView` draws from it and the
  mouse hit-tests against it. Tests in `tests/Sage.Tests/UI/PanelLayoutTests.cs`.
- **One piece of arithmetic, two readers.** A hit test that worked out row positions separately from
  the code that drew them is the same mistake as a rule applied in one place and asked in another
  (R17), and it fails the same way: the row that lights up is not the row that acts, on some window
  sizes only. Ten headless tests exist to say "what you drew there is what is under this point".
- **The mouse moves the same selection the keys move**, rather than having a hover of its own: a
  gamepad has no cursor, so the keyboard stays primary, and one notion of "the current row" means a
  click activates exactly what the reason line is talking about. Hover only applies when the pointer
  *moved*, so a cursor resting over row three does not drag the selection back every time a key moves
  it to row four.
- Left click acts on a row, right click is the second action (Delete's), the wheel moves the selection
  and the window follows it, and **a click outside the box closes the screen**, which is what most
  inventories do.
- **`in_cursor <x> <y>`** puts the pointer somewhere from a script, which is how this was checked end
  to end: move the cursor over the second row, press Enter with the keyboard, and the spell that gets
  readied is the one the pointer was over — which proves window pixels and UI pixels are the same
  pixels, the one thing headless tests cannot say.

### As built (text input, F38, 2026-09-23)
A field was the one widget the spellmaker could not do without — a spell needs a name — and it is the
piece that decides whether "our own UI" was the right call. It came to about a hundred lines.

- **Code:** `src/Sage.Simulation/UI/TextField.cs` (in the engine, like `Screen`: what a field contains is
  the name of a record about to exist), the typed-character buffer in
  `src/Sage.Client/Input/InputDevices.cs`, and the drawing and feeding in `ScreenSystem`. Tests in
  `tests/Sage.Tests/UI/TextFieldTests.cs`.
- **Characters, not keys** (08 §3.1). The window reports what was *typed*, after the operating system
  has applied the keyboard layout, the dead keys and the modifiers. Reading `Keys.A` and calling it
  "a" is how a name typed on an AZERTY keyboard comes out wrong, and there is no table that fixes it.
- **The buffer is cleared at the end of the frame**, not when input is polled: the window delivers
  characters *before* `Update` and a console script pushes them *during* it, so clearing at the start
  of input dropped whichever arrived first — which is exactly what happened to `in_type` at first.
- **Two things a field must not eat:** control characters (Return is "done" and Escape is "give up",
  both the screen's), and anything at all when ImGui has the keyboard — the dev console subscribes to
  the same window event, so a character typed into it would otherwise land in an open field too.
- **And one the screen must not:** `I`, `B` and `M` open screens *and* are letters. While a field has
  the keyboard the opener actions are skipped, so naming a spell "Misty Bind" does not open the
  inventory on the way. Escape, which is not a letter, still closes.
- **`in_type <text>`** pushes characters through the same buffer the window fills, so an automated
  check types what a player types (08 §3.5). One `in_tap` per frame, though: two taps of the same
  action in one console statement are one press, so scripts put a `wait` between them.

## 4. API sketch
```csharp
public sealed class DevUi                           // client module service (ImGui); dev builds and editor host only
{
    public void AddWindow(string menuPath, Action draw);   // e.g. "Debug/Physics"
    public bool WantsMouse { get; }  public bool WantsKeyboard { get; }   // feeds the UI input context (08)
}

// Built: a world resource installed by ClientModule. Screen pixels, queued in a Frame phase and
// drawn in Overlay. A game builds its own bars and panels out of these.
public sealed class UiDraw
{
    public Vector2 Size { get; }                       // the viewport, for placing against an edge
    public bool HasFont { get; }  public float LineHeight { get; }
    public void Rect(float x, float y, float width, float height, Color colour);
    public void Frame(float x, float y, float width, float height, Color colour, float thickness = 1);
    public void Text(float x, float y, string text, Color colour, float scale = 1);
    public void Image(Texture2D texture, Rectangle destination, Color colour, Rectangle? source = null);
    public Vector2 Measure(string text, float scale = 1);
}

// Built: in Sage.Simulation, so simulation code can say things without a client (13 §3).
public sealed class MessageLog                         // world resource; world.Say(...) is the shorthand
{
    public void Add(string text, MessageKind kind = MessageKind.Info, float seconds = 5);
    public ReadOnlySpan<Message> Messages { get; }      // newest last; each carries Remaining and Fade
}
```

### As built (rows that are sentences, 2026-09-24 — F24)
Dialogue was the first screen whose rows are prose rather than nouns, and it found two things in the
panel view that had never been asked of it:

- **A row's name is clipped to the room left by its detail column**, with an ellipsis. Before, a name and
  a right-aligned detail were drawn straight through each other — invisible while every name was
  "practice sword" and immediate when one became "Take this sword. I have no use for it."
- **A panel's title wraps** across as many lines as it needs, and `PanelLayout` grows the box and moves
  the rows down by exactly that much (`titleLines`). The wrapping is done in the view, which has the
  font, and cached against the title and width, because a panel is rebuilt when something changes but
  *drawn* every frame and cutting a sentence into substrings sixty times a second is the allocation the
  engine forbids itself (02 §4.6).

### As built (retained widgets, layout and focus, headless — 2026-09-30, issue #95, Phase 4c)
Screens outgrew lists: an inventory is a grid, loot is two lists side by side, a paper doll is slots
around a picture, and all of them want a gamepad. D8 still holds — our own UI, no Gum or Myra — and this
is its retained half. It is **headless**: widgets, layout, focus and hit testing, with no font, texture
or window, so a test builds an inventory, moves focus with the D-pad and clicks a slot. Drawing is #97,
building trees from ui_layout records and localised text is #96, the RPG screens' view-models #98.

- **Code:** a new base assembly, **`Sage.UI`** (`src/Sage.UI`), simulation-only (SAGE0024) and a base
  assembly, not a kit (SAGE0025): `Sage.Simulation` ← `Sage.UI` ← `Sage.Client` (decision D1). It
  references the simulation for `Rect` and nothing of physics or gameplay; it declared no plugin, record
  or component, being a library a screen builds trees with — since #96 it is one plugin, `sage.ui`, that
  owns its records and nothing else (below) (test: TheClientSitsOnTheRetainedUi)
  (test: NoBaseAssemblyReferencesALayerAboveIt). Its public API is declared (`PublicAPI.*.txt`) and all of
  it is experimental, **SAGE0125** (MAKING_A_GAME §10b). Games get the reference from `Sage.Sdk` (from
  source and from the `Sage.Player` package) and `games/Directory.Build.props`, but **no global using**:
  `Label`, `Button`, `Image` and `Grid` are names a game may well have, so a file says `using Sage.UI;`.
  Tests in `tests/Sage.Tests/UI/Widget*Tests.cs`.
- **Widgets:** `Box` (children by anchors), `Stack` (a row or a column), `Grid` (cells, row by row,
  optionally uniform), `Label`, `Button` (a label that takes focus; `Pressed`), `Image` (an asset path
  and a natural size; `ImageRect` keeps the aspect), `Bar` (`Value` in `Min..Max`; `FillRect`),
  `ItemList` (a column whose items are focus targets; `Selected`, `ItemActivated`), `Scroll` (one
  `Content`, clipped, scrolled by `Offset`) and one `Tooltip` per root. A container is a `Container`
  (`Add`, `Insert`, `Remove`, `Clear`); `Widget` has `Name` (and `Find`), `Data` (whatever a view-model
  hangs on it), `Style` (an id for #96/#97) and `TooltipText`. `WidgetTypes.Create("grid")` makes each
  built-in by the name `TypeName` returns, which is what a ui_layout record will say
  (test: EveryWidgetTypeIsMadeByItsNameAndTheTreeWalksInDrawingOrder).
- **Layout is two passes, Godot's containers rather than flexbox.** *Measure* goes up the tree (how big
  would you like to be in this much room?) and *arrange* down it (here is your rect). Each widget has
  `Margin` (outside), `Padding` (inside), `MinSize`, `HAlign`/`VAlign` (`Fill`, `Start`, `Center`, `End`:
  how it sits in the slot a Stack, Grid or Scroll gives it) and `Expand` (its share of a Stack's spare
  room) (test: AColumnStacksItsChildrenAndMeasuresTheirSumPlusSpacing)
  (test: ARowGivesWhatIsLeftToTheChildrenThatExpandAndAlignsTheRestAcross)
  (test: AGridPutsItsChildrenInCellsRowByRow) (test: PaddingAndMinSizeAndHiddenChildren). In a `Box`
  a child is placed by `Anchors` — each edge a fraction of the box, a point keeping the child's size or
  a span stretching it — with margins pushing in from the anchor lines, which is how a HUD pins a
  health bar to a corner (test: ABoxPlacesEachChildByItsAnchorsAndMargins).
- **Virtual units.** A `UiRoot` lays out in a design resolution (1280×720 unless told otherwise) scaled
  to the viewport by the smaller ratio, the other axis getting the extra room (Godot's "expand"
  aspect): on an ultrawide screen a bottom-right widget stays in the bottom-right corner rather than
  floating in from it. `Scale` and `ToPixels` are what the renderer multiplies by
  (test: LayoutIsInVirtualUnitsScaledToTheViewport).
- **Text without a font:** `ITextMeasure` (`Measure(text, scale)`, `LineHeight`) is all layout asks.
  The tests use `MonospaceTextMeasure`; the client will implement it over `BitmapFont` (#97), whose
  pixels at scale 1 are then virtual units.
- **Dirty flags, and zero allocation per frame.** A property that changes a size marks the widget and
  its ancestors dirty (`InvalidateMeasure`; a scroll offset only `InvalidateArrange`); `UiRoot.Layout`
  does nothing on a clean tree, and a clean widget answers both passes from its cache. What only the
  renderer cares about (a bar's value, focus, hover) moves `UiRoot.Version` without a layout, so #97 can
  cache its render plan against one number (test: OnlyADirtyTreeIsLaidOutAgain). Laying out and
  updating a clean screen allocates nothing (test: LayingOutAndUpdatingACleanTreeAllocatesNothing), and
  neither does navigating it, hovering, scrolling a list into view, or laying the whole of it out
  again after a resize (test: NavigatingAndRelayingOutAllocateNothing) — the grid's column and row
  arrays grow only with the grid, the focus chain is a list reused, and the renderer walks the tree
  with a struct visitor (`UiRoot.Walk`, `IWidgetVisitor`).
- **Focus is driven by a struct, `UiInput`:** `Navigate` (`Up`/`Down`/`Left`/`Right`, and `Next`/
  `Previous` for tab order), `Confirm`, `Back`, the pointer (position in pixels, moved, pressed, wheel)
  and `DeltaTime`. The client will fill it from the `ui` input context (#97); a test fills it by hand.
  `UiRoot.Update` returns a `UiResult`: what was activated, whether Back was pressed, whether focus
  moved and whether the pointer is over the UI (a click that is not is the world's, or closes the
  screen).
  - *Tab order* is `TabIndex`, then tree order, wrapping (test: TabOrderIsTabIndexThenTreeOrderAndWraps).
  - *Spatial navigation* picks the nearest focusable widget beyond the focused one's edge in that
    direction, and one in line always beats one off to the side, so the D-pad walks a grid by rows and
    columns, stops at its edges, and steps over a disabled slot instead of dropping diagonally
    (test: TheDPadMovesFocusAroundAGridAndThePointerHitsTheSlotUnderIt)
    (test: ADisabledButtonIsSkippedAndCannotBeActivated).
  - *The pointer* moves the same focus the keys move, and only when it moves — the panel screens' rule
    (F38) — and a click focuses and activates what is under it; hit testing respects a `Scroll`'s clip
    and never lands on the tooltip (test: HoverMovesFocusOnlyWhenThePointerMoves)
    (test: AScrollShowsPartOfItsContentAndClipsTheRest).
  - Focus onto an item inside a `Scroll` scrolls it into view, an `ItemList` selects what has focus,
    and the wheel scrolls what is under the pointer (test: AnItemListSelectsWhatHasFocusAndScrollsItIntoView).
    Removing, hiding or disabling the focused widget drops focus (test: RemovingTheFocusedWidgetDropsFocus).
  - The tooltip shows the `TooltipText` of what focus rests on (or the pointer, when it moved last)
    after `Delay` seconds, below it and kept on screen (test: TheTooltipFollowsFocusAfterItsDelay).
- **Not built (on purpose):** drawing, styles and fonts (#97); records, localisation keys and property
  binding (#96, built since: the next section); screens and view-models (#98) — `Screen`/`ScreenStack`/
  `PanelLayout` are unchanged and still draw every screen; explicit focus neighbours, modal focus scopes,
  drag and drop, text fields as widgets and word wrap (built since: neighbours and scopes with #343, the text field
  with #340, drag and drop with #346, wrap with #338).

### As built (style and layout records, screens and localisation — 2026-09-30, issue #96, Phase 4c)
The widgets of #95 built from content: a designer or a mod restyles, re-lays out or translates a screen
without C#, and a running game follows the edit. Still headless — nothing here draws (#97), and the RPG
screens' view-models are #98's.

- **Code:** `src/Sage.UI` — `UiRecords.cs` (the records and their JSON forms), `UiStyles.cs`,
  `UiView.cs` (the builder and the bound tree), `Binding.cs`, `UiScreens.cs`, `Localisation.cs` and
  `UiModule.cs`. Sage.UI is now the plugin **`sage.ui`** (`UiModule`, in `BasePlugins.All`, so the game,
  a dedicated server, `sage validate` and `sage schema` all read the same records); it owns the three
  record types and the `view_model` vocabulary and nothing else (test: TheClientSitsOnTheRetainedUi).
  It provides `Localisation`, `UiStyles` and `UiScreens` to modules that depend on it and to every
  world's resources. Tests in `tests/Sage.Tests/UI/UiRecordTests.cs`.
- **`ui_style`:** a font (a bitmap atlas; empty is the client's), `textScale`, `padding`, `borderWidth`,
  and the colours `textColour`, `background`, `border`, `fill` (a bar's) and `tint` (an image's), with
  `states` — `hover`, `focused`, `pressed`, `disabled` — each overriding only the colours it names.
  `base` inherits everything, states included, as any record's does. `UiStyles` resolves each style
  once per load (`UiStyle.Colours(UiState)`), `Get(widget.Style)` allocates nothing, an unknown id is
  the default style and one warning, and `StateOf(widget)` is disabled, pressed (the renderer's to say),
  focused, hovered or normal (test: AStyleInheritsItsBaseAndWorksOutEachState).
- **`ui_layout`:** a style and `nodes`, **a flat tree by name**, Godot-scene style: each node names its
  `widget` type (`WidgetTypes.Names`) and its `parent` (none: the layout's root, a `Box` with
  `Anchors.Fill`), and siblings keep their written order, then `order`. Flat so that a patch reaches
  one node — `"nodes": { "title": { "text": "@mymod.title" } }` merges into that node alone — or adds
  one anywhere, without copying the tree. A node sets what its widget has — `text`, `tooltip`,
  `source`/`naturalSize`, `minSize`, `margin`/`padding` (`4`, `[h, v]` or `[l, t, r, b]`), `hAlign`/
  `vAlign`, `expand`, `anchors` (`"bottom_right"`, `"fill"`… or `[minX, minY, maxX, maxY]`),
  `direction`, `spacing`, `columns`, `min`/`max`/`value`, `visible`, `enabled`, `focusable`,
  `tabIndex` — and what it leaves out keeps the widget's default; a node without a `style` has its
  parent's, and the style's padding and text scale apply where the node sets none
  (test: ALayoutRecordBuildsItsTreeInOrderWithItsStyles). Since #97 a style's padding applies only where
  the style is *applied* — a node naming it, or the layout's top nodes — not again on each node that
  inherits it, and the layout's root box carries no style (next section).
- **Bindings, allocation-conscious.** `bind` is a path into the view-model for the widget's main
  value — a label's or button's text, a bar's value, an image's source, a stack's, list's or grid's
  **rows** — and `bindings` names others (`text`, `tooltip`, `value`, `min`, `max`, `source`, `style`,
  `visible`, `enabled`, `data`, `rows`). A path is public fields and properties by name, ignoring case
  (`player.health`; `.` is the object itself); a null along it reads as nothing. Reflection runs once
  per (type, path): the members are compiled into one delegate returning a `UiValue` struct, so a
  number is never boxed, and what a binding shows is worked out again only when the value it read
  differs. A container bound to rows holds exactly one node, the template built for each row, bound to
  that row and carrying it as `Widget.Data`; rows are kept aside when the list shrinks and reused when
  it grows back. `args` fill a text's `{placeholders}` from the view-model, `count` choosing the plural
  form. `visibleIf` and `enabledIf` are #89's conditions, asked about the screen's `UiBindContext`
  (a world and a subject; none, and they hold); a hidden node's subtree is not read at all
  (test: AScreenBindsItsViewModelAndAsksItsConditions). Once built, a screen whose bar values change,
  whose conditions flip widgets on and off and whose rows come and go within what was made refreshes
  and lays out without allocating (test: BindingsAndConditionsRefreshWithoutAllocating).
- **`screen` and view-models:** a `screen` record is a `layout` and a `viewModel`, an entry of the
  **`view_model` vocabulary** (#28's mechanism, declared rather than registered):
  `[ViewModel("inventory")] class InventoryView : IViewModel`, whose `Refresh(in UiBindContext)` pulls
  from the world before the bindings are read. `UiScreens.OpenScreen(id, context)` makes a new one per
  screen, builds the layout and reads it once; `UiScreen.Refresh()` each frame; `Close()` takes it out
  of its parent. `UiScreens.BuildLayout(id)` builds a layout alone.
- **Hot reload, with no C#:** record hot reload watches `strings/` beside `data/`, and a reload — or
  the `lang` cvar changing — rebuilds the styles, reloads the tables and builds every open screen
  again, puts the new tree where the old one was and binds it at once
  (test: ChangingARecordReLaysOutAnOpenScreen).
- **Localisation** (D3; 05 §3.7 has the format): `@ns.key` in any text a layout shows is resolved when
  the screen is built, and `Localisation.Text`/`Format` resolve it for code. A missing key shows the key
  itself and logs one warning (test: AMissingKeyShowsTheKeyItselfAndWarnsOnce).
- **Checks at load, at their lines:** an unknown widget type (with the nearest), a parent that is not
  a node or is a leaf, a parent loop, a scroll with more than one child, `bind` on a widget with no
  main value, an unknown or inapplicable binding, a rows container without exactly one template, `args`
  on a widget with no text; for a screen, an unregistered view-model (with the nearest) and every path
  its layout binds that its view-model's type — or, in a row template, the rows' element type — has
  not got, with the nearest name (test: LayoutMistakesAreErrorsAtTheirLines). In a dev build and in
  `sage validate`, every `@key` in any record that no table has is a warning at its line
  (test: ValidateWarnsAboutMissingKeys).
- **Schemas:** `sage schema` writes `ui_style`, `ui_layout` and `screen` schemas; a node's `widget` is
  an enum of the widget types (test: TheWidgetTypeSchemaListsEveryWidgetType), a `style` or `layout`
  an id enum of those content has, and `viewModel` the registered view-models.
- **Not built:** drawing a style (#97 reads `UiStyles`, built since: the next section; a style's font
  does not yet change how a label measures — one `ITextMeasure` per root, built since with #338); the RPG screens' view-models (#98); a layout including
  another; binding paths with indexers or to the view-model from inside a row (both built since with #347);
  languages other than English's plural rule beyond a handful (`PluralRules`; CLDR's rules since #345).

### As built (drawing, input and animation — 2026-09-30, issue #97, Phase 4c)
The widgets of #95, styled and built from records by #96, on screen: drawn with `UiDraw`, driven by the
`ui` input context and the mouse, hosted beside the panel screens, and animated on frame time. What can
be asserted without a window is headless in `Sage.UI` — what gets drawn, in which order and under which
clip, the hosting and the input mapping — and the client only replays it.

- **Code:** `src/Sage.UI/UiRenderPlan.cs` (the plan, `NineSlice`, packed-colour blending),
  `src/Sage.UI/UiScreenStack.cs` (`UiScreenStack`, `UiLayer`, `UiTween`, the device-to-`UiInput`
  mapping); in the client `src/Sage.Client/Rendering/UiDraw.cs` (clips, nine-slice),
  `src/Sage.Client/UI/WidgetRenderer.cs` (`WidgetRenderer`, `BitmapFontMeasure`) and
  `src/Sage.Client/UI/ScreenSystem.cs`. The demo is the Sandbox's `sandbox:status` screen. Tests in
  `tests/Sage.Tests/UI/WidgetDrawingTests.cs` and `UiScreenStackTests.cs`; Sage.UI's internals are
  visible to the client, which is how the plan stays out of the public API.
- **`UiDraw` clips and nine-slices.** `PushClip`/`PopClip` keep a scissor stack, each clip intersected
  with the one it is pushed inside; drawing restarts the `SpriteBatch` where the clip changes (a scissor
  rectangle applies only between `Begin` and `End`), and a frame always ends unclipped. `NineSlice` cuts
  a texture by insets in texture pixels into corners that keep their size (`cornerScale` pixels per
  texel), edges that stretch one way and a middle that stretches both, shrinking the corners evenly when
  the destination is smaller than two of them and rounding shared edges the same way so the pieces meet
  without seams (test: ANineSliceKeepsItsCornersAndStretchesTheRest).
- **The render plan** is a flat list of commands in viewport pixels — `Rect`, `Border`, `Text`,
  `Image`, `PushClip`, `PopClip` — made by walking a `UiRoot` with a struct visitor. For each widget, in
  tree order, parents before children: its style's background, its style's `image` (nine-sliced by
  `slice`, tinted), its border (`borderWidth` × scale), then its content — a bar's fill (`FillRect`), an
  image's picture (its `ImageRect`, or the whole content rect when sliced), a label's text placed by
  `TextAlign` and centred down its content rect, sized `TextScale` × `UiRoot.Scale` pixels per font pixel.
  Colours come from `UiStyles.Get(widget.Style).Colours(StateOf(widget, pressed))`
  (test: ThePlanDrawsEachWidgetsStyleInTreeOrderInPixels)
  (test: AStylesImageIsDrawnOverItsBackgroundNineSliced) (test: TextSitsWhereItsAlignmentSaysAndCentredDown).
  A `Scroll` pushes its viewport (its clip intersected with its content rect) around what it holds and
  pops it after, restoring the outer clip; a leaf wholly outside its clip (a row scrolled out of a list)
  and a scroll wholly out of view are not drawn at all (test: AScrollClipsWhatItHoldsAndNestedClipsIntersect).
- **A style's box belongs where it is applied.** A `ui_layout` node without a style has its parent's
  (#96), so a window's style would otherwise paint its background and frame round every label in the
  window: background, image and border — and, in the layout builder, padding — are drawn and applied
  only where a widget's style differs from its parent's, while text colour and scale are inherited. The
  layout's root box, the whole screen, carries no style. A widget that wants its parent's box again names
  another style.
- **Cached, and allocation-free.** The plan is rebuilt only when the root's `Version`, `UiStyles.Version`,
  `Localisation.Version`, the pressed widget, the widget focus just left or the viewport changed
  (test: ThePlanIsRebuiltOnlyWhenWhatItShowsChanged). What moves every frame is applied by the client as
  it replays the plan — a layer's fade (alpha) and slide (y offset), and the focus highlight — so an open
  screen nobody touches costs one comparison. Hosting a screen (view-model, bindings, input, transitions)
  and bringing its plan up to date allocate nothing, both idle and while focus moves round it every frame
  and so rebuilds the plan every frame (test: AnOpenScreenIsHostedAndPlannedWithoutAllocating); an image's
  path is parsed once per source string.
- **Text** is measured by `BitmapFontMeasure`, the engine font's cell in *font* pixels (a 5×7 glyph in a
  6×9 cell), counted as `BitmapFont.Measure` counts: `textScale` 2 is an 18-unit line, as the HUD's text
  is at 720p. `UiScreenStack` measures with the same cell by default, so a layout is the same headless and
  on screen.
- **Hosting: `UiScreenStack`**, a resource of every world (from `UiModule`), holds **layers**: a screen
  record opened (`Open(id, context)`) or a tree a game built (`Push(widget, modal)`), each with its own
  `UiRoot` — its own focus, hover and tooltip. The top *modal* layer takes the input; a non-modal one (a
  HUD, #99) is drawn and never holds it. A modal screen opens with its first focusable widget focused (a
  gamepad has no pointer to start from), Back closes it, and a press on nothing of it closes it — a
  widget whose style draws a box counts as something, so a click on a window's empty part stays in the
  window (test: AScreenOpensFocusedFadesInAndBackFadesItOutAndClosesIt)
  (test: APressOutsideTheScreenClosesItButOneOnItsWindowDoesNot). `CloseOnBack`/`CloseOnClickOutside`
  turn those off per layer; `Activated` says what was confirmed or clicked; the widget held down (Confirm
  held, or the pointer held on the focused widget) is `Pressed`, which the renderer draws in the
  `pressed` state (test: OnlyTheTopLayerTakesInputAndAHudLayerNeverDoes). `Bind(action, screen)` and
  `Toggle` are `ScreenStack.Bind`'s rule — the key that opens a screen closes it — and the console has
  `ui_open <screen>` and `ui_close [all]`, which open a screen about the local player
  (test: AnActionTogglesItsScreenAndTheConsoleOpensAndClosesScreens).
- **`ScreenSystem` hosts both kinds.** Panel screens (`Screen`, `ScreenStack`) and widget screens run in
  the same Overlay system; a widget screen is drawn over the panels and, while one is open, takes the
  input and the panel under it waits. The `ui` input context is active while either is open, and the
  crosshair and the Sandbox's aiming HUD hide for either.
- **Input:** the panel screens' `MenuUp`/`MenuDown`/`MenuConfirm`/`MenuBack` (arrow keys, W/S, Enter,
  Escape; the D-pad, A and B) plus new `MenuLeft`/`MenuRight` (arrows, A/D, the D-pad) and `MenuTab`
  (Tab, the right shoulder; Shift+Tab goes back), in `engine_content/data/input.json`. One direction a
  frame, in a fixed order; the pointer in window pixels, pressed and held; the wheel in notches (120 a
  notch); and no pointer at all while a dev window has the mouse. A press that the stack finds on nothing
  of the top layer is its click-outside (test: TheMenuActionsAndTheMouseMapToUiInput).
- **Tweens on frame time.** `UiTween` eases a number with 4b's `Easing` over seconds it is *given*: the
  stack advances its layers by the frame's real time (clamped to 0.1 s), so transitions run with the game
  paused or slowed and never touch simulation state (test: ATweenEasesOnTheTimeItIsGiven). A layer fades
  in and slides up `SlideDistance` (24 units) over `OpenSeconds` (0.18 s, `CubicOut`), and fades and
  slides back out over `CloseSeconds` (0.12 s, `QuadIn`) — from wherever the opening had got to — before
  it leaves the stack and its screen closes. The **focus highlight** eases over `FocusSeconds` (0.12 s):
  the plan records the colour each end had (the newly focused widget's hover or normal colour, the
  previous one's focused colour) and the client blends by `FocusBlend`, so the plan does not change while
  it moves (test: FocusCarriesTheColourItEasesFromAndPressedWins).
- **`ui_style` gained `image` and `slice`:** a texture drawn behind a widget's content, over its
  background and multiplied by its `tint` — a window's frame, a button's plate — nine-sliced by `slice`
  (texture pixels, `4`, `[h, v]` or `[l, t, r, b]`), which also slices an `image` widget's picture.
  The stack's `TooltipStyle` styles every layer's tooltip, its text scale and padding included.
- **The demo:** `C` in the Sandbox (the `Status` action) or `ui_open status` opens `sandbox:status`
  (`games/Sandbox/content/data/ui.json`): a nine-sliced window (`textures/ui_frame.png`, made by
  `games/Sandbox/tools/make_ui_art.py`), the player's name, a health bar, a plural "Carrying N things"
  from `strings/en/sandbox.json`, a scrolling list of what is carried — each row a button whose tooltip
  is its weight — and a Close button, over the `sandbox_status` view-model (`games/Sandbox/StatusView.cs`),
  which keeps its strings until what they say changes. The screenshot shows it; D-pad or arrows walk the
  rows, Escape or `C` closes it with a fade.
- **Not built:** fonts per style (one `ITextMeasure` per stack), text clipped to a label or wrapped, a
  scroll bar, drag and drop, modal focus scopes within one layer, a transition per screen from content,
  and the RPG screens themselves (#98) and the HUD, journal, map and menus on widgets (#99). Buttons do
  what their screen's code says through `Activated`; a view-model cannot yet name an action from content.
  (Built since: fonts, wrap and clip with #338, focus scopes with #343, drag and drop with #346, actions from
  content with #344 and #347; a scroll bar and a transition per screen are still not built.)

### As built (focus scopes, neighbours and confirm prompts — 2026-10-06, issue #343, Phase 4q)
A menu that asks "overwrite this save?" needs a window that the D-pad cannot walk out of, and a menu laid out
by hand needs to say where Down goes when the nearest widget is the wrong one. Both are properties of a widget,
so a layout record sets them and a test drives them headless.

- **Code:** `src/Sage.UI/UiDialog.cs` (`UiDialog`, `UiDialogResult`), `Widget.FocusScope` and `FocusUp`/
  `FocusDown`/`FocusLeft`/`FocusRight` in `Widget.cs`, the scope handling in `UiRoot.cs`, and
  `UiScreenStack.Confirm` and `Message`. Tests in `tests/Sage.Tests/UI/FocusScopeTests.cs`.
- **A focus scope** is a widget with `FocusScope` set. While it is visible, focus stays inside it: Tab, the D-pad,
  the pointer and `UiRoot.Focus` reach nothing outside it, and a press outside it lands on nothing. When it hides,
  focus goes back to where it was before it showed. With several showing, the last in tree order, the one drawn on
  top, holds (test: AFocusScopeOverAMenuCannotBeLeftByGamepadOrMouse), and a scope inside a scope hands focus back
  to the outer one, not to the menu under both (test: ANestedScopeReturnsFocusToTheOuterOne). `UiRoot.ActiveScope`
  says which one holds, and `UiResult.Scope` carries it out of an update.
- **Explicit neighbours.** `FocusUp` and the rest name a widget by `Name`; the D-pad goes there instead of to the
  nearest widget that way. A name that is not in the tree (or the scope), or a widget that cannot take focus now, is
  passed over and the nearest is taken as before (test: ExplicitNeighboursOverrideSpatialNavigation). A
  `ui_layout` node sets `focusScope` and `focusUp`, `focusDown`, `focusLeft`, `focusRight`; a neighbour that is no
  node of the layout is a load error at its line
  (test: LayoutRecordsSetScopesAndNeighboursAndANeighbourThatIsNoNodeIsAnError).
- **Confirm and message prompts.** `UiScreenStack.Confirm(title, message, answered, confirm, cancel)` opens a
  modal layer over everything whose window is a focus scope: the confirm button answers true, the cancel button or
  Back answers false, and a press beside it does nothing (`CloseOnClickOutside` is off). Cancel has focus to begin
  with, the safe answer, unless `focusConfirm`. Answered, it fades out as any layer does and the layer under it has
  the input again with its focus where it was (test: AConfirmPromptOverAMenuTrapsFocusUntilAnsweredAndGivesItBack).
  `Message(title, message, closed)` is the same with one button. Texts starting with `@` are localisation keys;
  `DialogStyle` and `DialogButtonStyle` on the stack name the styles its window and buttons are drawn in.
- **Back while a scope shows in a screen is the scope's.** Back with a focus scope showing inside a layer goes to
  the view-model (to cancel whatever showed it) and never closes the layer under it
  (test: BackWithAScopeShowingInALayerDoesNotCloseIt).
- **Not built:** the prompt is built in C#, not from a layout record; its default button texts are English, not
  `@sage.*` keys; a long message does not wrap by itself (#338 wraps a label that says `wrap`); there is no
  Next/Previous neighbour for Tab.

### As built (data-driven buttons and view-model growth — 2026-10-06, issue #347, Phase 4q)
What a mod needs to add a screen with a working button and a reusable part from records alone.
