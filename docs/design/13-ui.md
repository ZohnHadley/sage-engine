# 13 — UI (short)

> **From the slice retrospective (2026-09-23), finding 1 — now F38.** The first vertical slice closed
> with **nothing the player can look at**: the spellmaker composes spells from the console, the
> inventory and the spellbook are console commands, and the HUD is four hand-placed rectangles. Every
> screen the slice needed turned out to be a `Log.Info`, which is why decision **D8** (Gum vs Myra vs
> our own) is still open. The next feature worth *playing* rather than *testing* is a screen. See
> [`../history/vertical-slice-2026-09-23.md`](../history/vertical-slice-2026-09-23.md).

## 1. Purpose and scope
Two different things:
1. **Developer UI:** the console, overlays, dev tools and the editor.
2. **Game UI:** HUD, menus, inventory, dialogue.

They use different technology on purpose. Expanded before inventory/dialogue screens are built.

## 3. Key decisions
- **Developer UI = Dear ImGui**, via the already vendored `third_party/MonoGame.ImGuiNet` (today's `Game1.GuiRenderer`).
  - It's used for the console (02 §4.2), `stat` overlays, dev windows and the whole editor (15).
  - Drawn in the Overlay pass (06).
  - Compiled only into dev builds and the editor host. **Not in `Shipping`.**
  - The **console** is the exception: v1 uses an ImGui window (dev builds). The `Shipping` console (`con_enable`, 01 §3.2) is a simple drop-down drawn with the game UI's font renderer, built with the game UI (D8).
- **Game UI = our own, on `UiDraw` (ARCHITECTURE D8, decided 2026-09-23; see "As built (the panel model)" below).** The candidates were **Gum** and **Myra** (both MonoGame UI libraries), against a small custom retained UI, on these criteria:
  - gamepad and keyboard navigation;
  - data-driven layouts (moddable, hot-reloadable);
  - text rendering with Unicode, localization keys (05) and runtime TTF fonts;
  - resolution scaling;
  - allocation behaviour;
  - licence.
- **Fonts:** anything but an MGCB `SpriteFont`, since MGCB is no longer part of the pipeline (05). A generated bitmap atlas is the v1 answer (see below); runtime TTF (e.g. FontStashSharp **[candidate, unverified]**) is the answer for localisation, when a language needs glyphs an atlas cannot hold.
- **v1 HUD before the decision:** a minimal immediate-mode HUD with `SpriteBatch` in the Overlay pass: health, crosshair, interaction prompt, and a pickup message.
- **Input** for UI goes through the `UI` context (08 §3.3), and text through `Window.TextInput` (08 §3.5).
- **UI reads simulation state; it never writes it.** Buttons that do something in the game ("use item") send commands through the input/command path (04 §3.1 rule), never direct component writes.

### As built (the v1 HUD, 2026-09-23)
- **Code:** `src/Sage.Client/Rendering/UiDraw.cs` (the queue), `UiRenderSystem.cs` (Overlay phase, one `SpriteBatch`, plus the crosshair), `src/Sage.Simulation/ECS/MessageLog.cs` (player-facing messages), and the game's own HUD in `games/Sandbox.Client/Hud.cs` (it moved there with the sim/client split, R15).
- **The engine draws none of the game's HUD.** It provides three things — `UiDraw` (rectangles, frames, text and images in screen pixels), a `MessageLog` every world has, and the crosshair — and the game composes them. What a health bar looks like is a game decision, and putting it in `Sage.Client` would have made the client know what health *is*. The crosshair is the exception: combat and the Use action both aim from the centre of the screen, so not drawing one is a handicap rather than a style (`ui_crosshair`, on by default, drawn only while a camera rig has the view).
- **Immediate mode, queued in a Frame phase, drawn in Overlay.** Anything running at display rate calls `Rect`/`Text`/`Image`; `UiRenderSystem` draws the queue and clears it. There are no widgets, no layout and no UI input handling — picking a real UI library (Gum, Myra, or something custom) is still open, and this is the smallest thing that let the slice show health, hands, a prompt and what just happened.
- **`MessageLog` is in the engine, not the client**, so a system can say "you picked something up" without knowing whether anything draws it — a headless server pushes into a log nobody reads. Since R13 (2026-09-23) `world.Say(...)` sends a `Said` game event and the log is the presentation system that reads it with a cursor (04 §3.1), which is why a message goes on screen at the next frame rather than the instant a tick says it. Messages carry a `MessageKind` (Info/Good/Bad) rather than a colour, because the simulation shouldn't name colours, and a `Fade` the HUD can use so a line leaves rather than vanishing.
- **The font is a grid of pixels we drew (R12, 2026-09-24).** The HUD font was an MGCB `SpriteFont` built from Consolas, which meant the build machine needed that font installed, glyph coverage was fixed at build time, and it was the last thing keeping MGCB in the build. It is now a **5×7 bitmap atlas the repository generates**: `engine_content/tools/make_font.py` draws 100 glyphs (printable ASCII plus `↑ ↓ • × …`, the characters the engine's own hint lines use) into a 128×56 `font.png`, and `src/Sage.Client/Rendering/BitmapFont.cs` reads it. Four constants are the whole contract between tool and runtime — an 8×8 cell, a 5×7 glyph in it, sixteen to a row, first code 32 — so a character's cell is `code - 32` and there is no metrics file to fall out of step. It draws at `PixelSize = 2`: a 14 px glyph on an 18 px line, about what Consolas 15 gave, so panels keep their shape. Characters are wider than that font's — 12 px against roughly 8 — which a panel that sizes itself from `Measure` absorbs and a hard-coded width would not.

  What this buys, beyond retiring MGCB: the engine ships no font it did not draw and licences nothing; the atlas is a PNG, so it hot-reloads like any texture and a mod can replace it; and **an unknown character draws as a gap instead of throwing**, where `SpriteBatch.DrawString` threw — an em dash in a hint line or a name a player typed used to take the frame and the process with it. What it costs is real too: one size, one weight, ASCII plus five extras, and no kerning. Runtime TTF is still the answer for localisation (05 §3.7). A missing font costs the text, not the HUD: bars and the crosshair still draw, and it logs once.
- **First-person hands (2026-09-23).** An `attack` record names a `viewmodel` sprite sheet — frame 0 at rest, the rest a swing — and the HUD draws it bottom-right, picking a frame from the `Melee` component's own phase and timer. So what you see in your hands is the simulation's swing, not an animation running alongside it, and equipping a different weapon changes it because the attack record changed. Daggerfall's own first-person weapons (`WEAPON*.CIF`, one idle pose and five-frame swings) import straight into that shape; the placeholder set draws a fist with three frames. It is drawn only while a camera rig has the view, so `cam_free` doesn't leave arms floating in mid-air.
- **Allocation.** The queue is pooled and the Sandbox's HUD caches its strings, rebuilding one only when what it says changes, so frames with the HUD up still allocate nothing (02 §4.6).
- **Not built (at the time):** menus, an inventory screen, dialogue, gamepad/keyboard navigation, layout, localisation, resolution scaling beyond raw pixels, and the Shipping console (§3). Screens, navigation and the first two of those arrived with F38 the same day — see "As built (screens)".

### As built (the panel model — F38's engine half, 2026-09-23)
A screen is two things: **what to show**, which is a simulation question, and **how to draw it**, which
needed the UI library decision **D8**, which had not been made when this was written. Those separate
cleanly, so the first half was built first; D8 was then decided as our own drawing on `UiDraw` (below).

- **Code:** `src/Sage.Simulation/UI/Panel.cs` (`PanelRow`, `Panel`) and
  `src/Sage.Gameplay/Rpg/GameplayPanels.cs` (the builders for spellbook, inventory, the spellmaker's
  effects and the spells a world has composed). Tests in `tests/Sage.Tests/UI/PanelTests.cs`.
- **A `Panel` is a titled list of rows**, and a row is everything a screen needs about one line: the
  `RecordId` to act on, a display name, a detail string ("12 mana", "2 kg"), a count, whether it is
  **selected** (readied, equipped) and whether it is **enabled** — with, when it is not, the reason in
  words.
- **The reason comes from the rule that would refuse it**, not from a second copy of the rule. The
  spellbook asks `AbilityRules.CanCast`, the same gates `AbilitySystem` applies and the AI consults
  (16 §3.3, R17); the bag asks `Items.CanEquip`, which `Equip` itself now uses. A greyed row and a
  refused action therefore cannot disagree, which is exactly the bug this shape exists to prevent.
- **Retained and rebuilt on demand**, never per frame: a screen rebuilds when it opens and after the
  player does something, because a row holds strings and rebuilding at display rate would allocate
  per row per frame (02 §4.6). `Panel.Version` bumps on each rebuild so a screen can cache layout.
- **The engine has no screens, so the console is the screen.** `spells` and `inv` print the *panel* —
  `Panel.Log` — which is the dogfooding: the console and a future screen read the same rows from the
  same builders and cannot drift apart. `ready <ability>` is the action a spellbook screen will call
  (`world.Ready`).
- **Why this is the useful half:** a headless test can now assert what a screen would show. "The
  spellbook greys out the spell you cannot afford and says why" is a test rather than a screenshot to
  squint at, and 12 of them came with this.
- **Built on 2026-09-23** — see "As built (screens)".

### As built (screens, F38, 2026-09-23)
**Decision D8: our own, on `UiDraw`.** With the panel model already answering what a screen shows, a
library would have contributed a list, a selection and a box; Gum brings an external layout editor and
Myra its own fonts and stylesheets, and both bring a second UI model beside the one the HUD uses. They
remain the right answer the day a screen outgrows a list.

- **Code:** `src/Sage.Simulation/UI/Screen.cs` (`Screen`, `ScreenStack`) and
  `src/Sage.Client/UI/ScreenSystem.cs` (`ScreenSystem`, `PanelView`). The game says which screens it
  has: `games/Sandbox.Client/Screens.cs` is 50 lines for a spellbook and a bag. Tests in
  `tests/Sage.Tests/UI/ScreenTests.cs`.
- **The split is the point.** A screen *is* a panel, a highlighted row, and what a button does to the
  world — all simulation, so `Screen` and `ScreenStack` are in the **engine** and a headless test opens
  a spellbook, moves down, presses Enter and asserts the readied spell changed. Only the drawing and
  the reading of input are in the client.
- **A game screen is a subclass with two methods:** `Build` (fill the panel) and `Activate` (what Enter
  does), plus `Alternate` for the second button. Everything else — wrapping selection, scrolling,
  rebuilding after an action, keeping the highlight inside a list that shrank — is in `ScreenStack`.
- **Input:** a new `ui` input map in the **UI context**. It reads its own keys first and then swallows
  the rest, so nobody walks about or swings behind an open inventory; the key that opened a screen
  closes it, and Escape closes without quitting the game. `MenuUp`/`MenuDown`/`MenuConfirm`/
  `MenuAlternate`/`MenuBack`, with `Inventory` (I) and `Spellbook` (B) opening the two.
- **Drawn in Overlay, before `UiRenderSystem`**, because a game's HUD queues in FrameUpdate and the last
  thing queued is on top. The crosshair and the game's viewmodel and interaction prompt hide while a
  screen is open — they belong to aiming, and there is nothing to aim at.
- **Two bugs a screenshot found and no test would have:** an interaction prompt and a fist painted
  across the spellbook (the layering above), and both stacks of a two-sword inventory drawing the
  "equipped" tick, because the tick was per item *id* and two swords are two stacks of one.
- **One crash it also found, in the engine:** `SpriteBatch.DrawString` throws on a character the font
  was not built with, so the first hint line with an arrow in it killed the process. Fonts now load
  with `DefaultCharacter = '?'` — a missing glyph is a visible '?', never a crash — and the HUD font
  gained the few glyphs the screens use.
- **Not built:** tabs or columns, drag and drop, and any screen that is not a list or a list with a
  field.

### As built (the mouse, F38, 2026-09-23)
The piece that decided whether the layout should be a *type*. It should.

- **Code:** `src/Sage.Simulation/UI/PanelLayout.cs` — where a screen's box, rows, field, reason and hint
  are, as plain arithmetic over a viewport size and a line height. `PanelView` draws from it and the
  mouse hit-tests against it. Tests in `tests/Sage.Tests/UI/PanelLayoutTests.cs`.
- **One piece of arithmetic, two readers.** A hit test that worked out row positions separately from
  the code that drew them is the same mistake as a rule applied in one place and asked in another
  (R17), and it fails the same way: the row that lights up is not the row that acts, on some window
  sizes only. Ten headless tests exist to say "what you drew there is what is under this point".
- **The mouse moves the same selection the keys move**, rather than having a hover of its own: a
  gamepad has no cursor, so the keyboard stays primary, and one notion of "the current row" means a
  click activates exactly what the reason line is talking about. Hover only applies when the pointer
  *moved*, so a cursor resting over row three does not drag the selection back every time a key moves
  it to row four.
- Left click acts on a row, right click is the second action (Delete's), the wheel moves the selection
  and the window follows it, and **a click outside the box closes the screen**, which is what most
  inventories do.
- **`in_cursor <x> <y>`** puts the pointer somewhere from a script, which is how this was checked end
  to end: move the cursor over the second row, press Enter with the keyboard, and the spell that gets
  readied is the one the pointer was over — which proves window pixels and UI pixels are the same
  pixels, the one thing headless tests cannot say.

### As built (text input, F38, 2026-09-23)
A field was the one widget the spellmaker could not do without — a spell needs a name — and it is the
piece that decides whether "our own UI" was the right call. It came to about a hundred lines.

- **Code:** `src/Sage.Simulation/UI/TextField.cs` (in the engine, like `Screen`: what a field contains is
  the name of a record about to exist), the typed-character buffer in
  `src/Sage.Client/Input/InputDevices.cs`, and the drawing and feeding in `ScreenSystem`. Tests in
  `tests/Sage.Tests/UI/TextFieldTests.cs`.
- **Characters, not keys** (08 §3.1). The window reports what was *typed*, after the operating system
  has applied the keyboard layout, the dead keys and the modifiers. Reading `Keys.A` and calling it
  "a" is how a name typed on an AZERTY keyboard comes out wrong, and there is no table that fixes it.
- **The buffer is cleared at the end of the frame**, not when input is polled: the window delivers
  characters *before* `Update` and a console script pushes them *during* it, so clearing at the start
  of input dropped whichever arrived first — which is exactly what happened to `in_type` at first.
- **Two things a field must not eat:** control characters (Return is "done" and Escape is "give up",
  both the screen's), and anything at all when ImGui has the keyboard — the dev console subscribes to
  the same window event, so a character typed into it would otherwise land in an open field too.
- **And one the screen must not:** `I`, `B` and `M` open screens *and* are letters. While a field has
  the keyboard the opener actions are skipped, so naming a spell "Misty Bind" does not open the
  inventory on the way. Escape, which is not a letter, still closes.
- **`in_type <text>`** pushes characters through the same buffer the window fills, so an automated
  check types what a player types (08 §3.5). One `in_tap` per frame, though: two taps of the same
  action in one console statement are one press, so scripts put a `wait` between them.

## 4. API sketch
```csharp
public sealed class DevUi                           // client module service (ImGui); dev builds and editor host only
{
    public void AddWindow(string menuPath, Action draw);   // e.g. "Debug/Physics"
    public bool WantsMouse { get; }  public bool WantsKeyboard { get; }   // feeds the UI input context (08)
}

// Built: a world resource installed by ClientModule. Screen pixels, queued in a Frame phase and
// drawn in Overlay. A game builds its own bars and panels out of these.
public sealed class UiDraw
{
    public Vector2 Size { get; }                       // the viewport, for placing against an edge
    public bool HasFont { get; }  public float LineHeight { get; }
    public void Rect(float x, float y, float width, float height, Color colour);
    public void Frame(float x, float y, float width, float height, Color colour, float thickness = 1);
    public void Text(float x, float y, string text, Color colour, float scale = 1);
    public void Image(Texture2D texture, Rectangle destination, Color colour, Rectangle? source = null);
    public Vector2 Measure(string text, float scale = 1);
}

// Built: in Sage.Simulation, so simulation code can say things without a client (13 §3).
public sealed class MessageLog                         // world resource; world.Say(...) is the shorthand
{
    public void Add(string text, MessageKind kind = MessageKind.Info, float seconds = 5);
    public ReadOnlySpan<Message> Messages { get; }      // newest last; each carries Remaining and Fade
}
```

## 11. v1 scope vs later
- **v1:** the ImGui console + `stat` overlays (**built in migration step 2**; until the game UI exists, a Shipping build with `con_enable 1` reuses the ImGui console window); the immediate-mode HUD; log category `UI`.
- **Later:** options (with rebinding, 08); localization switching. D8 is decided (our own UI), and the bag, spellbook, spellmaker and dialogue screens exist. REDESIGN §4.7 plans the data-driven layouts and styles.

### As built (rows that are sentences, 2026-09-24 — F24)
Dialogue was the first screen whose rows are prose rather than nouns, and it found two things in the
panel view that had never been asked of it:

- **A row's name is clipped to the room left by its detail column**, with an ellipsis. Before, a name and
  a right-aligned detail were drawn straight through each other — invisible while every name was
  "practice sword" and immediate when one became "Take this sword. I have no use for it."
- **A panel's title wraps** across as many lines as it needs, and `PanelLayout` grows the box and moves
  the rows down by exactly that much (`titleLines`). The wrapping is done in the view, which has the
  font, and cached against the title and width, because a panel is rebuilt when something changes but
  *drawn* every frame and cutting a sentence into substrings sixty times a second is the allocation the
  engine forbids itself (02 §4.6).
