## 2. Known limits and what is not verified

- **A code mod is not sandboxed.** It runs with the game's full trust. It is flagged (`[contains code: not sandboxed]` in
  `mod_list`, the boot report and `sage mods`) and never auto-downloaded (the engine has no download path), and MODDING §8c
  says so plainly. A Workshop subscription is never consent to run code.
- **Not verified: the on-screen `.fx` reload.** Editing a mod's `shaders/*.fx` under `-game ... -mods` and seeing it swap
  needs mgfxc, which runs on Windows or under Wine, and a GPU; Linux CI has neither. The logic is tested headless with a
  fake compiler (`IShaderCompiler`); a Windows smoke run should confirm it before anything says "verified on screen".
- **Packing a code mod needs the mod built first.** `sage mods pack` takes `bin/` as built (every configuration there) and
  refuses a code mod built in none ("is not built (build the mod, then pack it)"); a mod with `.fx` files needs mgfxc or an
  up-to-date `.mgfxo` beside each source.
- **Hot-reloading a file under `@ns/` reloads the literal path**, `@ns/...`, not the namespaced asset that uses it; restart
  to see it. A zip is read-only and is never hot reloaded.
- **Scene and placement `place` lists are not keyed**: the editor saves a game level as a patch that restates the whole
  `place` list (a placement may have no id), which relies on replace. Only `inventory.items`, quest `stages` and dialogue
  `nodes` are.
- **Components in a code mod need the host.** A mod that declares ECS components or tags is refused in a process whose
  component schema is already built (a second app, a test) and, once loaded, is never unloaded: the schema keeps the type.
- **`sage package` copies mounts as folders**; it does not write zips, and `sage-mod-code` is not a template.
- **The kit's `rpg:mods` screen does not show the code flag** (`ModsView.ModRow.ContainsCode` is there; the layout and its
  goldens are a later change). The Workshop has an interface and no implementation.
- The backlog from 4f, 4r and 10b still holds (their handoffs' §2).

## 5. Traps

- **Pack a code mod after building it, and build every configuration you ship.** `bin/{config}/X.dll` resolves with the
  host's configuration; a package holding only `bin/Debug` fails in a Development or Shipping host.
- **`ModPackage.Pack` leaves the root `obj/` out and dot files out.** A code mod's intermediates carry the builder's absolute
  paths; do not put anything the mod needs under `obj/` or a dot folder.
- **Code mods load before any `Init` and before any world.** Registries seal and the ECS schema builds after them, so a mod
  cannot be added later; `[Plugin("<mod id>")]` or `[Plugin("<mod id>.<name>")]` is required, and the mod's modules run after
  the game's unless `[RequiresPlugin]` says otherwise.
- **Process caches must not pin a collectible type.** Anything keyed by a `Type` or an assembly (upgraders, metadata,
  `SystemDeclaration`, `SaveSerializer`'s transient and from-placement checks) is a `ConditionalWeakTable` or is not cached;
  a new cache that holds a type strongly makes a mod's context never unload.
  `CodeModUnloadTests.TheCodeModsContextUnloadsWhenTheAppIsDisposed` is in the `ProcessWideState` collection, and System.Text.Json's
  own emitted-accessor cache drops an entry about a second after its last use, at its next use.
- **A bare asset path is a mod's own only if no non-mod mount has it.** The test is on the game, engine, kit and `--mounts`
  mounts; shipping a path the game has is an override, and two mods doing so are a conflict. To replace one mod's own asset,
  write `@<ns>/<path>`.
- **`MountLookup` is the one lookup.** `FolderMount`, `AssemblyContentMount` and `ZipMount` share it; a new kind of mount
  that does its own path matching misses namespaces and `@ns/`.
- **A zip's `.fx` is never compiled at run time.** Pack it compiled; `AssetChecks` counts a `.mgfxo` as present through its
  `.fx` only in a folder mount.
- **A keyed edit with a bare key means the record's namespace.** `lantern` in the village's content is `village:lantern`; a
  foreign mod writes the key in full. Several entries with one key are all edited, and `FieldWrite.IsUnder` treats `[` as a
  separator, so a keyed write conflicts only with the same key.
- **A record-level `"replace": true` keeps `base`; an entry-level one keeps its key.** Its write is a Set at the object's
  path (a whole record is a Set per field and one at `""`, shown as `(record)`).
- **The mods exit game changed.** `rival_trade` has its own falchion and replaces the lantern picture on purpose, so
  `sage mods tests/games/mods` reports one conflict (the trader's name), and `ModsExitTests.TheModsGameValidates_WithItsMods`
  asserts one. A PR that touches the game's mods must keep that number.
- **Counts and schemas after a merge.** `check_docs --fix` for the counts; `schemas/` regenerated after merging `main` (every
  object schema gained `replace`, keyed entries `$remove`), as in every phase.
- **Merge order mattered.** #397 and #398 both touched `ZipMount` and the lookups (#398's `MountLookup.Find` in the zip mount
  was the lead's merge), and #396's packed code mods were written after #397 and #398 were in its branch; `PublicAPI.Unshipped.txt`
  files take both sets of lines.
