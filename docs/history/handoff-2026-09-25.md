## 2. The lesson, which is the reason this handoff exists

**Point lights were dead in the shipped game for a day, and all 514 tests passed.**

Moving the `light` prefab part into its own `LightsModule` was right. What was wrong is that
`Sage.Host/Program.cs` kept a *second*, hand-written list of gameplay modules and never called
`AddGameplay`. The new module was added in every test and in no build anybody plays. Lamps spawned with
no `PointLight` on them. The game said so on every boot — one line,
`ERROR Records  sandbox:light: no prefab part 'light'` — and nobody read it.

Three things went wrong, and only the first is about modules:

1. **A check that runs against a different configuration from the one that ships is not a check of the
   thing that ships.** The tests were not weak. They were thorough about the wrong list. Anywhere the
   shipped path and the tested path are assembled separately, this is waiting.
2. **A screenshot is not evidence unless something in it could have been different.** Lighting was
   "verified" three times by looking at a picture and finding it warm — twice at a **wooden floor in
   daylight**, which reads exactly like lamplight. The `r_stats` light count settled it in one run.
   Prefer a number; if it must be a picture, take the A/B and compare the bytes.
3. **An `Archive` cvar set by a scripted run persists into every later run.** `+r_lights 0` for one
   comparison wrote `r_lights "0"` into `user/<game>/config.cfg`, and every run after it had lighting
   off — including the runs used to judge whether lighting worked. Check the cvar, or read the number.

An `ERROR` in the log meant the game was telling the truth the whole time. **Grep the log for `ERROR`
after every scripted run** — it is one line in the verification loop and it would have caught this
before the commit.

## 4. Gaps worth knowing about before you promise anything

Found by sweeping the code, the docs and the roadmap on 2026-09-25; the detail is in
[`readiness-2026-09-24.md`](readiness-2026-09-24.md), corrected the same day.

- **Nothing spawned at run time survives a save.** `World.MakePersistent` is called only by tests — no
  spawn path calls it.
- **Extension points nothing calls:** `PhysicsSpace.SetVelocity` (knockback or an explosion would
  silently do nothing), `AudioMixer.SetBusVolume` (a volume slider has nothing to write to),
  `CVarRegistry.Complete` (Tab-completion, built, never wired), `World.RemoveSystem`,
  `GameplayTags.HasAll`/`HasAny`. `CommandLatch.SetView` was one of these until this session needed it.
  **A public method with no callers is a feature that has never run.**
- **Streaming keeps what a game placed.** Unload destroys only `SectorOwned` entities; a prop or NPC a
  game puts in the world is never unloaded, and an NPC a few sectors out stands over a heightfield
  whose collision has gone.
- **A missing record is a silent default.** `RecordStore.Get<T>` logs once per call site and returns a
  default-constructed record, so a typo'd id becomes zero damage or a silent sound, with the complaint
  deduplicated away.
- **A bare id inside a `patch`** resolves against the namespace of the record being patched. If the
  engine owns a record of that name, it binds to the engine's instead of the game's, silently.
- **25 cross-doc contradictions** were found; the three that were mapper-facing are fixed. The build-step
  lists (§14 in each design doc) are the least maintained sections in the corpus — 04's and 10's are the
  worst, listing as unbuilt things the same docs describe as built.
