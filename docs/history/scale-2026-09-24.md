# What a full world costs (2026-09-24) — R18

The [readiness review](readiness-2026-09-24.md) §3 said the tests proved correctness and not fitness:
the largest test created two hundred entities, the Sandbox placed twenty-five, and **every performance
claim in these docs was an assumption**. This is the measurement that replaces them, and the two bugs
it found on the way.

Numbers are from one machine and one build, and that is the point of writing the machine down: the
next person compares like with like.

| | |
|---|---|
| Machine | Windows 10, 4 CPUs, one GPU |
| Build | Development (optimised, dev tools on, profiler on) |
| Scene | The Sandbox, plus **2,000 tree prefabs** spawned with `scale_spawn 2000 tree` |
| World | 2,201 entities · 9 terrain sectors · 12 physics bodies, **2,031 statics** |

---

## 1. What a tick costs

The fixed schedule runs at 60 Hz, so the budget is **16.67 ms**. It uses **0.76 ms of it (4.6%)**.

| Phase | ms | The systems that matter |
|---|---|---|
| Commands | 0.025 | `AIThinkSystem` 0.021 |
| PrePhysics | 0.206 | `CharacterMovementSystem` **0.193** |
| Physics | 0.359 | `PhysicsStepSystem` 0.358 (2,031 statics) |
| PostPhysics | 0.011 | write-back 0.009 |
| TransformPropagation | 0.060 | twice a tick, 2,201 entities |
| Gameplay | 0.086 | `EffectSystem` 0.055 |
| Animation | 0.011 | |
| Late | 0.005 | streaming 0.003 |
| **Total** | **≈0.76** | |

## 2. What a frame costs

| Phase | ms | Note |
|---|---|---|
| FrameUpdate | 0.012 | HUD, camera rig |
| Extract | 0.872 | **`SpriteExtract` 0.806** |
| Render | 0.168 | |
| Overlay | 0.028 | |
| **Total** | **≈1.08** | |

Drawn: 39 mesh items, **482 sprites**, **1,670 culled**, **65 draw calls**, 71,540 triangles, 6 material
switches. 152 meshes, 28 textures and 7 materials resident.

**`SpriteExtract` is the single largest cost in the engine at this size** — three quarters of the frame
and more than the whole simulation tick. It walks every sprite, picks a direction group and sorts; the
culling happens after. That is where the next optimisation is, and it has a number to beat now.

## 3. Memory and allocation

| | |
|---|---|
| Managed heap, Sandbox only | 43 MB (before a GC) |
| Managed heap, +2,000 trees | 31 MB (after; a gen2 collection ran between) |
| Spawning 2,000 prefabs | **19 ms** |
| Steady-state allocation per tick | **40 bytes** |

Those 40 bytes are Bepu's own profiler inside `Timestep` (TODO #41), not the engine's. **Everything
else in a full tick allocates nothing** — 2,000 entities, 100 thinking creatures, streaming and all.

That was not true when this measurement started.

## 4. The two bugs the measurement found

Both were invisible to every other test, because correctness tests do not look at the allocator.

### `PawnIntent` was boxed twice per phase, per character, per tick — ~3.2 KB each
The phase contract (R16) snapshots a component and compares it after every later phase. The comparison
used `EqualityComparer<T>.Default`, which for a struct **without** `IEquatable<T>` falls back to
`ValueType.Equals(object)` and boxes both sides. One character cost 3,200 bytes a tick; a hundred cost
**320 KB a tick**, and the feature that did it exists only to help developers.

Fixed by implementing `IEquatable<PawnIntent>`, and `PhaseContracts` now **warns once** when a
component is put under a contract without it, so the next one is caught by a log line rather than by a
profiler.

### `Enum.HasFlag` in the AI's schedule choice — ~23 B per creature per tick
`ChooseSchedule` asked its conditions ten times a think through `Enum.HasFlag`, which takes a boxed
`Enum` and is only sometimes seen through by the JIT. With the contract fixed this was the *entire*
remaining allocation in a hundred-creature world; replacing it with a bitwise test took the AI to
zero. The same call in the `ai_debug` overlay went with it.

**Together: 323 KB per tick down to 40 bytes**, a factor of about 8,000, in a world of 2,000 entities.

## 5. What the tests now hold

Wall-clock thresholds were deliberately not asserted — they pass on this machine and fail on a slower
one, and a test that gets disabled for flakiness protects nothing. `tests/Sage.Tests/Streaming/ScaleTests.cs`
asserts what is true on any machine:

- a 2,000-entity world **runs**, keeps its entities, and its creatures still notice the player;
- a full world **allocates nothing per tick** beyond an empty one (the measurement above, as a test);
- cost grows **sub-quadratically**: four times the entities must cost less than eight times the time,
  which catches somebody's accidental loop over "everything else" without caring how fast the box is;
- 2,000 entities **survive an origin rebase** with their world positions intact (R6 at size).

## 6. What to look at next

1. **`SpriteExtract`, 0.806 ms** — three quarters of the frame. Cull before extracting rather than
   after, and the direction-group choice is per sprite per frame.
2. **`CharacterMovementSystem`, 0.193 ms** for a handful of characters — it is sweep-heavy, and a
   Warband-like will want hundreds of them.
3. **2,031 statics for 2,000 trees.** Every tree carries a collider; most will never be touched. Both
   the streaming rings and dormancy (14 §3) exist to answer that, and neither is doing it yet.
4. The tick has **15.9 ms of headroom** at this size, so the honest next step is a bigger scene rather
   than an optimisation: 10,000 entities, and creatures in the hundreds rather than a hundred.
