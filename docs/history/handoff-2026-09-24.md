# Handoff — 2026-09-24

Written at the end of the session that finished R6, F14, R18 and F4, and brought up to date at the end
of the one that finished **R12, F16, F17, R19 and F28**. It is for whoever picks the engine up next with
no memory of how it got here: where it stands, how to prove that for yourself, what to do next, and the
specific traps this engine has already sprung on somebody.

---

## 1. Where it stands

`sage-engine` is a C#/MonoGame engine for a **Daggerfall-like** first-person RPG, with an HL1-like, a
Lugaru-like and a Warband-like named as later targets. Multiplayer is deliberately **not** built;
["readiness rules"](../../ARCHITECTURE.md) keep the option open. Modding is **data + trusted C# mods**.

The vertical slice is walkable, fightable, lootable, castable, resumable, unbounded and audible; since
the last update it also has **interiors, doors that open, an editor that edits, and a second game**:

| | |
|---|---|
| Size | 116 console commands, 46 record types, 1272 headless tests <!-- counts --> |
| Records | `ability`, `attack`, `item`, `map`, `material`, `placements`, `prefab`, `quest`, `sound`, `sprite_sheet`, `weather`, … |
| Tests | Green in Debug and Development; see §3 for why Shipping is not a test configuration |
| Phases | 13 — Fixed: Commands, PrePhysics, Physics, PostPhysics, Gameplay, AI, Animation, EntityIO, Late; Frame: FrameUpdate, Extract, Render, Overlay |
| Steady-state allocation | 40 bytes a tick with 2,000 entities and 100 thinking creatures ([the numbers](scale-2026-09-24.md)) |

What that means concretely: you spawn in a streamed, unbounded world; a firebug chases you, swings and
throws ember bolts; you fight back with a sword you picked up or a spell you composed in the spellmaker;
a campfire hums where it is standing; you save, quit, load, and it is all still true a hundred sectors
from the origin. You can also walk up to a hut drawn in TrenchBroom, press E, watch the door slide aside
and be greeted by the trigger volume inside.

**Three things arrived this session that change how the engine is used**, rather than what it can do:

- **Levels are real** (F16/F17). `.map` files from TrenchBroom become convex hulls and meshes;
  `classname` spawns a prefab; brush entities become doors, lifts and trigger volumes wired in map data
  (`"OnUse" "!self,Open"`), checked when the level loads.
- **Nothing is built before it runs** (R12). MGCB is gone: models, textures, sounds and the font are all
  read at runtime off the VFS, so a mod or a player can add a file the build never saw.
- **The words are checked against the code** (R19). `tools/check_docs.py` verifies links, vocabulary,
  test citations and every number a document quotes about the engine or the repository. Run it beside
  the build; `--fix` writes the counts. It exists because three features in a row ended with the code
  right and something it *said about itself* wrong.

**It is not production ready**, and [`readiness-2026-09-24.md`](readiness-2026-09-24.md) is the honest
account of why — read it before promising anything, and note that two of its complaints have since been
answered. The short version as it stands now: no animation beyond sprites, no gizmos or undo in the
editor, no asset pipeline for real content beyond runtime loaders, no shadows and no lightmaps (lamps
light a room, four per surface, which is enough for a hut and not for a town), and a renderer that is
one material system and four passes.

**If you are here to make a game rather than the engine**, start at
[`docs/MAKING_A_GAME.md`](../MAKING_A_GAME.md) and run [`games/Hello`](../../games/Hello), which is the
smallest game this engine runs — four files, and it is in the solution so it cannot rot.

## 3. How to build, test and verify

```bash
dotnet build -c Debug && dotnet build -c Development && dotnet build -c Shipping   # all three must build
dotnet test tests/Sage.Tests -c Development       # 490 tests, ~18 s
python engine_content/tools/make_engine_textures.py   # the engine's own textures (the particle dot)
python games/Sandbox/tools/make_placeholder_art.py    # regenerates the placeholder sprites
python games/Sandbox/tools/make_placeholder_audio.py  # and the placeholder sounds
```

**The suite is for Debug and Development only.** Shipping must *build* and *run*, but
`dotnet test -c Shipping` fails six tests on purpose: they assert behaviour Shipping deliberately
compiles out — `Log.Trace`/`Log.Debug` existing, `Assert.Dev` throwing on a missing component, the phase
contracts reporting a late write, the profiler recording phases, and `DevOnly` cvars being registered.
One of them says so in its own assertion message. It looks like a broken engine and is not one; if you
ever want them green everywhere they need a Shipping-aware skip, and nobody has decided that is worth
doing.

Run the game, scripted, and read what it did:

```bash
./src/Sage.Host/bin/Development/net8.0/Sage.Host.exe -game games/Sandbox \
  +sv_cheats 1 +log_file_level Trace +log_level audio trace \
  +ent_spawn sword_pickup +wait 0.6 +in_tap Use +wait 0.3 \
  +equip practice_sword +wait 0.3 +in_tap Attack +wait 0.5 \
  +snd_stats +screenshot +quit 1
```

- `+<cvar> <value>` and `+<command> <args>` run in order after `config.cfg`; `wait <seconds>` defers the
  rest of the queue; `quit <seconds>` ends the run, so a check never needs a human.
- `in_tap` / `in_hold` / `in_look` / `in_axis` / `in_type` inject input, which is the only way to test
  anything that needs a key press.
- Cheat-flagged commands (`snd_play`, `equip`, `ent_spawn`, `warp`, `give`…) need `+sv_cheats 1` first,
  and say so when they refuse.
- Logs land in `user/sandbox/logs/`, screenshots in `user/sandbox/screenshots/` — and a screenshot can
  be read back and looked at, which is how the origin-rebase camera bug was caught.
- **`+log_file_level Trace` is not optional** in that line. Without it the file sink keeps whatever
  `config.cfg` last saved (`Debug` here), `log_level audio trace` appears to work, and not one trace line
  reaches disk. This paragraph exists because the line above was written without it and printed nothing.

### The verification loop that catches what tests cannot

Everything client-side — the renderer, the UI, audio — is **invisible to the headless tests by
construction**, because the tests have no device. This engine has shipped that bug twice: audio readers
on the wrong event queue (the game fought in silence while every test passed) and a sound record with no
code path. So for anything client-side:

1. Turn the subsystem's log category up (`+log_level audio trace`, `+log_level assets debug`, …).
2. Drive it with `in_tap`/`+command` and `wait`.
3. Read the log and assert against what it *says happened*, not what should have.
4. Then write the headless test for whatever part of it *is* a decision, and move that decision into
   `Sage.Engine` if it is not there already.
5. Run `python tools/check_docs.py --tests N` with whatever `dotnet test` reported, so that what you
   then write about it is checked against what you built.

Every feature this session was verified this way, and the pattern held: **the errors were never in the
logic**. They were in the claims — a promise the code did not keep, a number nobody counted, a menu item
a script could not press. What running the thing catches is the first kind; what the checker catches is
the second; the third is why every menu item here is also a console command.

Step 4 is the whole architectural pattern: `AudioMixer`/`IAudioBackend`, `Panel`/`PanelView`,
`Screen`/`ScreenSystem`, `RenderSnapshot`/`Renderer`. The decision is engine-side and tested; the device
is client-side and decides nothing.

## 4. What to do next

The second milestone is **complete**, and the session that finished it also finished the three items
that were meant to come after. What was done, briefly, so you know what not to redo:

| Item | What landed |
|---|---|
| **R12** | MonoGame 3.8.5.1, `HiDef`, and **MGCB gone**: models (`.glb`), textures, sounds and the font are all read at runtime. Nothing is built ahead of time but shaders |
| **F16** | **Levels.** `.map` files from TrenchBroom: brushes become convex hulls and one mesh per texture, `classname` spawns a prefab, `fgd_export` tells the editor what this game has |
| **F17** | **Entity I/O.** Outputs wired to inputs in map data and checked at load, movers (doors, lifts), trigger volumes — the hut has a door you open and a room that greets you |
| **R19** | `tools/check_docs.py`, because the three items above each ended with the code right and its own words wrong |
| **F28** | **An editor that edits something**: placement documents, outliner, editable inspector, and a Shipping build with no editor or ImGui in it at all |
| **F2's last leftover** | **Lighting indoors.** Point lights: a `PointLight` component and a `light` classname, the strongest four by influence chosen per draw (engine-side and tested), added in `common.fxh` on top of the sun. The Sandbox's hut has two lamps and is no longer a dark grey box; `r_lights 0` gives the old look back |

**What is actually next** — nothing forces the order, so pick by what the next game needs:

1. **F29 gizmos and picking, then F30 undo/redo.** The editor can select and edit but not *drag*, and
   every edit is permanent until you close without saving. The command log F30 wants is also where
   multi-select and "revert to prefab" will live.
2. **The source generator** (09 §3.2). Several things now queue behind it: per-entity keys in the FGD
   and in maps, declared save fields, and an inspector that knows what a field *means* rather than what
   type it happens to be. It waits until the component set stops moving, and the component set has been
   still for a while now.
3. **Lightmaps** (06 §3.9). Four lights at a time is enough for a room; a level the size of a town wants
   light baked into the geometry, which is what HL1 did and what F16's brushes are already shaped for.
4. **Phase 7 multiplayer**, still behind the readiness rules, and still the largest single item.

**If you are here to make a game rather than the engine**, start at
[`docs/MAKING_A_GAME.md`](../MAKING_A_GAME.md) and run [`games/Hello`](../../games/Hello): the smallest
game this engine runs, four files, in the solution and covered by tests so it cannot rot.

## 5. Sharp edges this engine has already sprung

Each of these cost a debugging session at least once. They are in the code comments too, but this is the
list.

- **An event belongs to the queue of the schedule that *sent* it.** Gameplay sends from `Schedule.Fixed`;
  a Frame-phase system that registers a `Frame` reader finds an empty queue for ever, silently. This is
  what made the first audio system play nothing while every test passed.
- **An event must carry what its reader needs.** `world.Destroy` is immediate, and every reader is later
  than the sender, so an event that names an entity may describe a corpse. `Used` carries the item and
  the point for exactly this reason (04 §3.2).
- **A cue names a moment as well as a reaction.** An ability has `castCues` *and* `cues`; one list raised
  at both the launch and the landing puts the burst in the caster's hand.
- **A bare record id inside a `patch` resolves in the *patched* record's namespace**, not the file's. A
  game patching `sage:physical` with `"sound": "hit_flesh"` points at `sage:hit_flesh`, which does not
  exist. Write ids in full inside a patch until R11 fixes it. Validation does catch it, loudly.
- **`EqualityComparer<T>.Default` boxes** a struct that does not implement `IEquatable<T>`, and
  **`Enum.HasFlag` boxes** its argument. Both showed up as kilobytes per tick in R18's scale test and
  neither was visible to any correctness test. `scale_report` measures the **Fixed** schedule only —
  Frame-phase allocation is not covered by anything yet.
- **Everything that holds a position must subscribe to a rebase** (`world.Origin().Rebased`): physics,
  the renderer, the audio mixer, debug shapes with a duration, the editor camera. Scene coordinates and
  saves are **origin-space**, so a save carries the sector it was written in.
- **`log_file_level` in `user/sandbox/config.cfg` caps the log file.** If it is `Debug`, no `TRACE` line
  reaches disk no matter what `log_level` says, and you will conclude your logging is broken. It is an
  `Archive` cvar, so whatever you set with `+log_file_level` is saved for next time.
- **Daggerfall's art is Bethesda's.** `games/Sandbox/content/data/daggerfall.json` and
  `content/textures/daggerfall/` are gitignored and the importer reads the user's own install. Never
  commit any of it. The placeholders are *generated* by the two Python scripts for the same reason.
- **A press is not whatever a device says.** Input is ignored entirely while the window is not focused,
  edges come from the raw device state rather than the consumed one, and a trigger bound to a button has
  hysteresis (08 §3.7, review #60). If you add a device or an action kind, those three rules are in
  `Sage.Engine/Input/InputGating.cs` and are the reason the player no longer swings at nothing.
- **`[SavedResource]` on a class saves nothing by itself.** The type has to be registered with
  `Engine.Saves.RegisterResource<T>()` or the attribute is decoration — three resources were "saved" and
  were not (09, "Sharp edge"). If you add one, write the round-trip test with it.
- ~~**`SpriteBatch.DrawString` throws on a glyph the font lacks.**~~ Gone with `SpriteFont` in R12: the
  bitmap font draws an unknown character as a gap, because a missing glyph is a content problem and not
  a reason to lose the process.
- **A disposed texture draws as black, not as an exception.** Hot-reloading `textures/font.png` disposed
  the atlas while `UiRenderSystem` still held the `BitmapFont` wrapping it, and GL happily drew every
  label as a black box with nothing logged anywhere. Two rules came out of it: `Reload` drops the
  wrapper along with the texture it wrapped, and **a system asks the content service for an asset each
  frame rather than holding one** — the ask is a dictionary lookup, and holding is how you end up
  drawing from something that was freed.

- **A character on the `default` physics layer falls through the world.** A character sweeps against
  everything *except its own layer* — which is what lets creatures pass through each other — and terrain
  collision is on `default`. The Sandbox never noticed because all of its characters name a layer; the
  guide's example game, written the obvious way, fell for ever while the camera followed it down, so
  every direction looked like empty sky. It warns now
  (test: ACharacterOnTheDefaultLayerIsToldThatItWillIgnoreTheGround).
- **A level's furniture outlives the level unless something says otherwise.** Unloading took the walls
  and left the watcher standing in the field, and reloading added another. Geometry and spawned entities
  carry *different* markers for that reason (15 §10a), and the same shape of bug is worth suspecting
  whenever two halves of the engine clean up after one thing.
- **Anything holding a world position follows a rebase** — including a level's own `Position`, which is
  not an entity and so does not move itself (R6). The list of subscribers is in 14 §3; adding to it is
  cheaper than the afternoon spent finding out.
- **A mapper's mistake must cost that line, not the level.** Every loader written this session refuses
  one brush, one wire, one placement, and says which line — because the alternative is a level that will
  not load and a person with no idea why.

## 7. House rules

- **Commits:** never add a `Co-Authored-By: Claude` trailer. Mention Claude as plain text in the body
  instead, e.g. `Written with Claude Code (Claude Opus 5).` Commit messages here are prose that explains
  *why*, in the same voice as the code comments.
- **A claim ships with the test that proves it** (R19). An "As built" bullet that says the engine does
  something cites the test: `(test: WalkingIntoATriggerVolumeFiresOnStartTouch)`. `tools/check_docs.py`
  checks the citation resolves, along with links, command and cvar names, and the counts on a
  `<!-- counts -->` line. Run it beside the build; `--fix` writes the counts, `--self-test` checks the
  checker. It exists because three features in a row ended with the code right and the words wrong.
- **After every change, do a second pass** before reporting it done: re-read the diff looking for gaps
  and inconsistencies, not for typos. Every second pass in this session found something real, and three
  of the five F4 findings were things no test could have caught.
- **Assessments go in the docs**, not in chat: a dated write-up in `docs/history/`, R/F items in
  `TODO.md`, and a pointer in the relevant `docs/design/NN-*.md`. **Verify every count against the code
  before writing it** (`grep -rhoE '\[Record\("[a-z_]+"' --include=*.cs src/ games/ | sort -u | wc -l`,
  and so on) — a number in a doc that the code disagrees with is worse than no number.
- **Prove a test is not vacuous.** Reintroduce the bug, watch the test fail, then put it back. This is
  how the cue-timing test, the streaming margin and the rebase subscription were all confirmed.
- **Zero allocation in the steady state** (02 §4.6). It is measured, and the measurement is cheap to run.
